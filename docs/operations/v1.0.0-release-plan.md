## Version / Tag Policy

### Finding

`pkg/version/version.go` currently has source default `Version = "0.6.0-dev"`.
GoReleaser injects the real version at build time via ldflags:

```
-X github.com/he8um/daryaft/pkg/version.Version={{.Version}}
```

When `goreleaser release` is run on the `v1.0.0` tag, `{{.Version}}` resolves
to `1.0.0` (GoReleaser strips the leading `v`). The resulting binary reports
`version: 1.0.0, built_by: goreleaser`. This is the correct behavior and is
already the established project convention.

### Recommendation: Do NOT change the source default before tagging

The source default `0.6.0-dev` in `pkg/version/version.go` is intentionally a
development-oriented string. It signals "this is a source build, not a release
build." The GoReleaser ldflags path is the correct injection mechanism for
release version metadata.

**Do not change `Version = "0.6.0-dev"` before tagging v1.0.0.**

The stable release binary will correctly report `1.0.0` because of the
GoReleaser ldflags injection. Changing the source default to `1.0.0` is both
unnecessary and risky — it could cause confusion if source builds after the
release still carry `1.0.0` while the codebase has moved forward.

### Post-release source default (optional, post-1.0 decision)

After the v1.0.0 release is published, the source default can optionally be
updated to `1.1.0-dev` or similar to indicate active post-1.0 development. This
is a post-1.0 housekeeping commit, not a pre-release requirement.

## Pre-Release Preparation

### Step 1: Confirm current state

```bash
git status
git log --oneline --decorate --graph --all -10
git tag --list "v1.0.0" "v0.6.0-rc.*"
```

Expected: working tree clean, HEAD at `main`, no existing `v1.0.0` tag.

### Step 2: Pull latest

```bash
git pull --ff-only
```

Confirm no unexpected commits arrived. If the pull brings changes, re-run all
quality checks from the beginning.

### Step 3: Run all final quality checks

Run every check in [v1.0.0 Go/No-Go Checklist](v1.0.0-go-no-go.md) Section B.

```bash
go test ./...
go build ./...
go test -race ./internal/downloader
go test -race ./internal/tui
make lint
make security
goreleaser check
make rc-check
make release-check
git diff --check
sh -n scripts/manual-qa-server.sh
```

All must exit 0. If any fail, stop. Fix the issue on `main`. Then restart from
Step 1.

### Step 4: Review release notes

Open `docs/operations/release-notes-v1.0.0.md`. Confirm:
- Known Limitations are accurate.
- Install URLs reference `v1.0.0` (they should already).
- The `Status: DRAFT` notice at the top should be removed or replaced with
  `Status: RELEASED` after the release is published (not before tagging).

## Tagging

### Step 5: Create the annotated tag

```bash
git tag -a v1.0.0 -m "Daryaft v1.0.0"
```

Do not create a lightweight tag. The annotated tag is required for GoReleaser
to inject the correct version.

Verify the tag:

```bash
git tag --list v1.0.0
git show v1.0.0 --stat
git describe --tags --exact-match
```

### Step 6: Push the tag

```bash
git push origin v1.0.0
```

This will trigger GitHub Actions. Confirm the workflow passes:
- `Go test/build (ubuntu-latest)` — PASS
- `Go test/build (macos-latest)` — PASS
- `goreleaser-check` — PASS
- `lint` — PASS
- `security` — PASS

**Wait for CI to go green before building release artifacts.**

## Release Build

### Finding: `.goreleaser.yml` has no `release:` block

The current `.goreleaser.yml` does not have an explicit `release:` block. This
means `goreleaser release` (without `--skip=publish`) will attempt to create
and publish a GitHub release automatically using the `GITHUB_TOKEN` environment
variable.

**Recommended path: build artifacts locally first, then publish via `gh`.**

This gives full visibility and control before anything is published publicly.

### Option A (Recommended): Build locally, publish with `gh`

This is the safest path given the current configuration.

#### Step 7A: Build release artifacts locally (no publish)

```bash
git checkout v1.0.0
goreleaser release --clean --skip=publish
```

This builds all platform archives and `checksums.txt` into `dist/` without
publishing to GitHub. The `--skip=publish` flag is critical.

Inspect artifacts:

```bash
find dist -maxdepth 2 -type f | sort
cat dist/checksums.txt
```

Expected files:
- `dist/daryaft_linux_amd64.tar.gz`
- `dist/daryaft_linux_arm64.tar.gz`
- `dist/daryaft_darwin_amd64.tar.gz`
- `dist/daryaft_darwin_arm64.tar.gz`
- `dist/checksums.txt`

Verify checksums:

```bash
shasum -a 256 dist/*.tar.gz
# Compare against dist/checksums.txt entries
```

Spot-check the platform binary:

```bash
mkdir -p /tmp/daryaft-v1-check
tar -xzf dist/daryaft_darwin_arm64.tar.gz -C /tmp/daryaft-v1-check
/tmp/daryaft-v1-check/daryaft version
/tmp/daryaft-v1-check/daryaft version --json
/tmp/daryaft-v1-check/daryaft doctor
```

Expected: `version: 1.0.0`, `built_by: goreleaser`, doctor exits 0.

#### Step 8A: Create GitHub release and upload assets

```bash
gh release create v1.0.0 \
  --title "Daryaft v1.0.0" \
  --notes-file docs/operations/release-notes-v1.0.0.md \
  --verify-tag
```

Do NOT pass `--prerelease`. This is the stable public release.

Then upload assets:

```bash
gh release upload v1.0.0 \
  dist/daryaft_linux_amd64.tar.gz \
  dist/daryaft_linux_arm64.tar.gz \
  dist/daryaft_darwin_amd64.tar.gz \
  dist/daryaft_darwin_arm64.tar.gz \
  dist/checksums.txt
```

### Option B (Alternative): Let GoReleaser publish directly

If `GITHUB_TOKEN` is set and you are confident the config is correct, run:

```bash
goreleaser release --clean
```

This will create the GitHub release and upload assets in one step. GoReleaser
uses the existing `.goreleaser.yml` which does not have package-manager
publishing enabled.

**Risk**: Less visibility into what GoReleaser does before publishing. If
anything goes wrong mid-process, the release may be partially published.

Option A is preferred for the first stable release.

## Rollback / Fix-Forward

### Do not delete or retag v1.0.0 unless absolutely necessary.

If a bug is found after v1.0.0 is published:
- Fix on `main`.
- Run all quality checks.
- Tag `v1.0.1` and follow this release plan from Step 1.
- Prefer fix-forward over retagging.

The only valid reason to remove a published release is a critical security
vulnerability that would cause active harm to users. In that case:
- Do NOT delete the tag.
- Mark the GitHub release as a pre-release or create a visible security advisory.
- Ship `v1.0.1` immediately with the fix.
